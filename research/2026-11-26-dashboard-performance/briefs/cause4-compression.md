# Brief: compress large control responses between the server and the gateway

You build one pull request in 3xDevOps/cloudfield (Go server and CLI; read CLAUDE.md first and follow it: code style, docs, commits, no AI author lines, "This PR was made with the help of <tool>." in the description). State in your first message to your parent (session run-d4aesztxwh, `aether-internal send --to run-d4aesztxwh`) which model you run as. Work at high effort: this is a protocol change on the path every dashboard call takes.

## Why

The dashboard reaches the server through `cloudfield gui` (the local gateway, `internal/localgw`), which carries each call over an SSH channel (`control` subsystem: one JSON line out, one JSON line back; client `internal/protocol/client.go`, server `internal/sshd/control.go`, `serveControl` / `writeJSONLine`). Nothing on that hop is compressed: SSH offers no compression and the Edge relay's WebSockets have it off. Measured on a seeded store (research/2026-11-26-dashboard-performance/evidence/payload-sizes.txt on branch `cloudfield/run-performance-overhaul-of-the-clou-d4aesztxwh`, draft PR #1175): a 1,000-event `workspace.timeline` page is 356,410 bytes and gzips to 21,634; `run.list` for 600 sessions is 350,941 bytes and gzips to 23,543. Lanes reads up to 25 such pages per workspace; cold open reads `run.list`. On a slow or throttled link these bytes are the wait.

## Goal

Large control RESPONSES from server to gateway are compressed when, and only when, both ends agreed to it.

## Requirements (the owner's terms; all are merge conditions)

1. **Negotiated.** An old gateway with a new server and a new gateway with an old server must both keep working, uncompressed, with no error and no extra round trip per call. Design the negotiation yourself after reading how the gateway and server already learn about each other (`server.info`, the subsystem header and `maxSubsystemHeaderBytes` in `internal/sshd/control.go`, `internal/cli/channel.go` `openSubsystem`, `protocol.NewClient`, `internal/protocol/gateway.go`). Note that since #1178 the gateway keeps control channels open and reuses them (`internal/localgw/backend.go`, `keptReads`), and other clients of the control channel exist (the CLI in `cmd/aether`, `internal/ops`, the MCP connector, tests): a client that never asks must get exactly today's bytes. Write down the wire format in docs/ (find where the control channel is documented; `docs/local-gateway.md` and the protocol guide).
2. **Both mixed-version directions tested** with real ends, not mocks: new client against a server that does not know the feature, and a client that does not ask against the new server. Tests in the packages you touch; an integration-level test if one exists for the control channel (`internal/sshd` test helpers `newTestEnv`, `controlClient`).
3. **CPU cost measured on one CPU, with a size threshold.** Responses below a threshold are sent as today. Measure, with Go benchmarks you add (`go test -bench`, GOMAXPROCS=1), compress and decompress time and ratio for realistic payloads at several sizes (build them from the seed tool's shapes: see `research/2026-11-26-dashboard-performance/seed/main.go` on the research branch for event and run shapes, or marshal `protocol.Event` and run records yourself) and for an incompressible payload (a base64 file read: `files.read`, `run.patch` responses can be up to hundreds of MiB, see `responseLineLimit` in `internal/protocol/client.go`). Choose the algorithm (standard library first; a new dependency needs a strong, measured reason and must be named in your report as needing the owner's approval), the level and the threshold from those numbers, and say what a 350 KB page costs the server in CPU against what it saves on the wire. Decide what to do with responses that do not shrink (send as is) and with very large ones (streaming, memory: the server must not hold a second full copy of a 64 MiB file if avoidable; state what it does).
4. **Limits stay enforced.** `MaxLineBytes` and `maxBlobResponseBytes` bound a response line today. A compressed frame must not let a small frame expand without bound on the gateway (decompression bomb): bound the decompressed size by the same limits, and test it.
5. **Security section in the PR description**, written for a separate security reviewer who will attack it: compression beside secrets in one stream. Say, with file references, whether any single response mixes attacker-chosen text with secrets the attacker should not learn (CRIME/BREACH shape: an attacker who can inject text into a response and observe its compressed size on the wire). Consider who can observe sizes (the hosted Edge relay sees ciphertext lengths of the SSH stream; a network observer), who can inject text (another member's session titles, messages, file contents, agent output in `run.list`, timelines, transcripts), and which responses carry secrets (tokens, invite codes, credentials, private payloads addressed to one member). If such responses exist, exclude them (an allowlist of methods that may be compressed is acceptable and probably right: start from the large read-only ones, `workspace.timeline`, `run.list`, `run.acp.history`, `changes.list`, and justify each), and say so.
6. **No behaviour change otherwise**: errors, cancellation, the gateway's watchdog and channel reuse, the server's per-frame timers and admission (`controlFrameReader`), streams (attach, acp, events) untouched.
