## 1. The store

- **Design:** One engine, SQLite, through the pure-Go driver `modernc.org/sqlite`. go.mod:46; internal/store/sqlite.go:18.
- **Design:** `store.Open` pragmas: `busy_timeout(5000)`, `foreign_keys(1)`, `journal_mode(WAL)`, `synchronous(NORMAL)`, `secure_delete(1)`, and `_txlock=immediate` so write transactions take the write lock at `BEGIN`. internal/store/sqlite.go:35-43, 52-53.
- **Design:** The pool has no `SetMaxOpenConns`; only `SetMaxIdleConns(16)`. So the store may hold several connections that write, serialised by SQLite's file lock and the 5 s busy timeout. internal/store/sqlite.go:58-60.
- **Design:** The event log is a second `sql.DB` on the same file (`events.OpenSQLiteLog(StorePath(...))`). Its writer pool is capped at one connection (`SetMaxOpenConns(1)`); reads use a separate read-only pool of 4 (`query_only(1)`, `readConns = 4`). internal/events/sqlitelog.go:45, 55-75; internal/server/server.go:314-326.
- **Design:** The comment on `Open` says the store and the event log "share one write lock, so a commit must not hold it across an fsync", which is why `synchronous` is NORMAL. internal/store/sqlite.go:42-43.
- **Design:** The write lock is SQLite's: one writer at a time on `aether.db`. The only extra in-process lock is the bus mutex, which holds sequence assignment, the log write and fan-out together: "concurrent publishes (and Subscribe) serialize on the disk write - a deliberate trade for a gapless, ordered cursor". internal/events/inproc.go:44-52.
- **Design:** The `events` table is created by `internal/events`, outside the store's migration ladder, though it lives in the same file. One migration rebuilds it and says to "keep eventsSchema ... in step". internal/events/sqlitelog.go:18-33; internal/store/migrate.go:316-326, 403-405.
- **Design:** Every event must name a workspace (`ErrNoWorkspace`); `seq` is one counter across all workspaces and is the replay cursor. internal/events/bus.go:23-26; internal/events/inproc.go:57-59, 99.
- **Design:** The sequence counter is held in memory (`InProc.seq`), seeded at start from `LastSeq`, and written into each insert as an explicit `seq`. A driver error after a commit makes the bus re-read `LastSeq` "so the next publish never reuses a persisted seq". So a write by another process would collide on the primary key on this process's next publish, which would fail once and then resync. internal/events/inproc.go:29-42, 99, 124-134. (The consequence is read from the code, not run.)
- **Design:** Live streams come from the in-process bus, not from the database. `Publish` persists, then enqueues to each matching subscriber's buffer (default 256 events, drop-oldest, never blocks). `Subscribe` registers first, then replays from the log up to the join cursor, so replay and live have no gap. internal/events/inproc.go:16-19, 138-142, 146-149, 257-258; internal/events/bus.go:92-100.
- **Design:** One payload type is `Ephemeral` (typing); it is fanned out with no sequence and no log write. internal/events/inproc.go:82-89; internal/events/event.go:423-429.
- **Design:** Both the SSH events subsystem and the dashboard WebSocket build their subscription with `events.SubscribeWire`. A client resumes with `after_seq`; the stream closes with code 1012 on a drop, a restart or a buffer overflow. internal/events/stream.go:20-47; docs/local-gateway.md:2576-2606.
- **Design:** Is there a `Store` interface? Yes: `store.Store`, one interface assembled from about 80 methods plus embedded sub-interfaces (`WorkspaceAccessStore`, `AgentLoginStore`, `CostStore`, `ServerUpdateStore`, `PushStore`, `AssistantStore`, ...). Its one implementation is `*store.DB`, asserted by `var _ Store = (*DB)(nil)`. internal/store/store.go:44, 130-143; internal/store/sqlite.go:27.
- **Design:** The interface does not fully hide SQLite. Every constructor and most consumers take `store.Store`, but the server keeps the concrete `*store.DB` (`db *store.DB`), and some consumers type-assert to it (`cfg.Store.(*store.DB)` in the scheduler, `store.IdentityStore` in sshd). `database/sql` appears outside `internal/store`, `internal/events` and `internal/edge/store` only in an error-mapping comment in the scheduler. internal/server/server.go:218; internal/scheduler/scheduler.go:789; internal/sshd/edge.go:55-60; internal/scheduler/scheduler.go:958.
- **Design:** The event log has its own two-interface seam: `EventLog` (Append, Read, ReadBefore, LastSeq, Close) and the optional `EventLogByID`. `Bus` is an interface too; the only implementation is `InProc`. internal/events/bus.go:126-168.
- **Design:** `store.Open` runs `migrate` itself, so any process that opens the store migrates it. The ladder is idempotent and safe "under concurrent Open calls on the same file". A binary older than the database fails with `database schema version N is newer than this binary supports (M)`. internal/store/sqlite.go:61; internal/store/migrate.go:2723-2760.
- **Design:** Second-process openers of `aether.db`, found by grepping for `store.Open`, `OpenChannelFile`, `OpenSQLiteLog` and `sql.Open` in cmd/ and internal/: the `cloudfield-server edge claim-code` path (two helpers: one reads the named admin member, one lists members to refuse a code without `--admin`), `cloudfield-server device approve|review`, and `cloudfield-server member role`. Each opens the full store (so migrates) while the server may be running. cmd/aether-server/edge.go:280, 310, 489; cmd/aether-server/member.go:30.
- **Design:** `cloudfield-server update` reads and writes the release channel through `OpenChannelFile`, which opens the database without migrating and reads the schema version first. The server reads the change at its next release check. internal/store/serverupdate.go:316-322; cmd/aether-server/channel.go:22, 53.
- **Design:** The docs call the member-role command a direct write: it "writes the role straight to the server's database ... The role applies to connections that are already open". The git transport re-checks access "every revalidateInterval for writes made outside it". docs/teams.md:238-243; internal/sshd/session.go:251-255.
- **Design:** Backup before migration exists only on the update path. When the release's `store_schema` is above the database's, the server stops, takes a consistent copy with `VACUUM INTO` (opened `mode=ro`) to `<data-dir>/server-update/aether.db.pre-update`, then starts the new binary; if the new server does not finish starting, both binaries and the copy are restored. internal/serverupdate/apply.go:270-280; internal/serverupdate/trial.go:73, 205-216, 266-268; internal/store/serverupdate.go:386-401; docs/install.md:779-783, 825-837.
- **Design:** `store.Open` itself takes no copy before migrating (no backup call in `Open` or `migrate`). A restart onto a newer binary installed by hand migrates without one. internal/store/sqlite.go:44-66; internal/store/migrate.go:2731-2760. (Absence read from the code.)
- **Design:** The server refuses a downgrade across a schema: `this database is at schema <n> and <tag> only knows schema <m>; it could not open it`. docs/install.md:1008-1011; internal/serverupdate/preflight.go:110-116.
- **Design:** Host-local state outside the database that the database refers to: `runs.worktree` and `run_repos.worktree` hold absolute server paths; `member_terminals.container_id` holds a container id. internal/store/migrate.go:452, 611, 1941; internal/domain/domain.go:866-870.
- **Design:** Per-run supervision state is a JSON sidecar per run, `<data-dir>/scheduler/<run-id>.json` (container id, paused, retained, destroy pending, evidence pending, login member ...), plus `scheduler/terminals/`. internal/scheduler/state.go:416-436, 591-596; internal/server/server.go:473.
- **Design:** Deleted preferences are tombstoned in a file, `<data-dir>/preference-tombstones`, and re-deleted at start, "so restoring an older database does not bring it back". docs/privacy.md:557-566; internal/server/server.go:317-320.
- **Design:** The edge has its own SQLite database, `edge.db`, with a schema compat floor and a copy taken before each schema upgrade. internal/edge/service/service.go:282; internal/edge/store/edgestore.go:293-298, 315-329; docs/privacy.md:326-328.
- **Not established:** The size of any real `aether.db`. install.md shows a "9.1 GB database" only inside an example of update output. docs/install.md:795.
- **Not established:** Whether any other process opens `aether.db`. The grep above found only those openers; `aether-internal` subcommands and the `vm-monitor` process were not read file by file.

## 2. Git

- **Design:** One bare repository per workspace, `<data-dir>/repos/<workspace-id>.git`, made by `git init --bare`. docs/install.md:1144; internal/gitengine/engine.go:220-225.
- **Design:** A session checkout on the server's disk is a self-contained `git clone --local` of the bare repo into `<data-dir>/checkouts/<run-id>/` (hard-linked objects), then `checkout -b <branch> <base-commit>`. It is a clone, not a `git worktree`, although install.md and the `Run.Worktree` field call it a worktree. internal/gitengine/checkout.go:125-131, 163-183; docs/install.md:1145; internal/domain/domain.go:869.
- **Design:** The branch name is claimed in the bare repo at launch: `cloudfield/run-<slug>-<short-id>`, with the full run id as fallback. The claim is "a ref write in the workspace bare repo rather than a read-then-use check". internal/gitengine/checkout.go:210-223.
- **Design:** Commits land in the checkout. They reach the bare repo (and so clients) when `PublishRunBranch` fetches the run's branch from the checkout into `repos/`, forced, called from the scheduler at supervision, launch, steer, recovery and evidence. internal/gitengine/checkout.go:401-445; internal/scheduler/supervise.go:193; internal/scheduler/evidence.go:204, 291, 324.
- **Design:** VM sessions: the checkout is a qcow2 disk, `<data-dir>/checkouts/<run-id>/disk.qcow2`, a copy-on-write layer over a prepared disk per workspace, base commit and owner under `<data-dir>/vm/images/prepared/`; each checkout disk is a 128 GiB sparse filesystem. The host-side checkout directory holds only run metadata. docs/vm-guest.md:604-612; internal/gitengine/vm.go:31-35, 54-72; docs/install.md:1145.
- **Design:** The server gets a VM session's commits through the guest's git service (`aether-internal guest git-service`, gRPC on vsock port 1100). `Watch` streams each snapshot and each moved HEAD to the server; `Objects` streams a pack; the server indexes it with `git index-pack --strict` into `<run-id>.diffsnap/` and publishes HEAD by fetching from that store into the workspace repo. A snapshot or HEAD "counts as delivered only once the server acknowledges it". docs/vm-guest.md:618-650, 660-676; internal/gitengine/vm_watch.go:381.
- **Design:** The final commit of a VM session is built on the server (`git commit-tree`, signed), so "the member's signing key never enters the VM". If the VM is gone before the final commit, the server boots it without the agent's command to make it. docs/vm-guest.md:682-699; docs/failure-handling.md:1010-1020.
- **Design:** `<run-id>.diffsnap/` is a git object store beside the checkout. It "reads its fork point from `repos/`", so the two are restored together. A VM session's keeps its fork point under `refs/aether/sessions/<run-id>` in the workspace repo so `git gc` cannot prune it. docs/install.md:1159-1161; docs/vm-guest.md:722-726; internal/gitengine/snapshot.go:20-27.
- **Design:** All git-engine locks are in-process: `sync.Mutex` fields for repo init, file write, snapshots per run, repo maintenance, alternates and VM receive. No file lock. internal/gitengine/engine.go:114-138; internal/gitengine/snapshot.go:59-67. The SSH side adds a per-workspace in-process read/write lock around a transfer. internal/sshd/session.go:180-186.
- **Design:** Clients push and pull over the same SSH port: an `exec` request of `git-upload-pack` or `git-receive-pack <workspace>` is served by `Git.UploadPack`/`ReceivePack`, gated by `View` or `Push` and re-checked during the transfer. docs/networking.md:3-6; internal/sshd/session.go:82-96, 153-220.
- **Design:** Source mirror. Who fetches: the server, inside `internal/mirror` calling the git engine's built-in fetch (HTTPS or SSH only). Credential: `--auth github` uses the configuring admin's gh token read from their home (`GitHubCredentials func(ctx, member)`); `--auth deploy-key` uses an ed25519 key at `<data-dir>/mirrors/<workspace>/private_key.<generation>` (0600); `public` uses none. Locks: one in-process `sync.Mutex` per workspace in `Service.locks`; `Capture` refreshes under it. Mirror settings are a DB row (`workspace_mirrors`). internal/mirror/service.go:53-67, 128-135, 460-526; internal/gitengine/engine.go:66-72; docs/security.md:703-718.
- **Design:** Pushing the mirrored base branch is refused; a scheduled session refreshes the mirror first and creates no session if that fails. docs/teams.md:379-385.
- **Design:** Publish to GitHub is done by `git` and `gh` inside the session's own container or VM, via `runtime.Exec`, with "the run's" environment: "The execution/account environment is the run's; never substitute the server's." So the credential is the launcher's gh token in `~/.config/gh/hosts.yml` of the home mounted there. internal/runrepo/service.go:20-36, 52-53; docs/security.md:483-487, 497-504.
- **Design:** The checkout's `origin` is repointed at the workspace's upstream so a push from inside the run reaches it; the clone otherwise points at a server path that "does not exist inside the run container". internal/gitengine/checkout.go:132-136, 197-202.
- **Design:** Evidence also keeps refs in the workspace repo (`refs/aether/evidence/`) and a deferred `git gc` marker file there. internal/gitengine/evidence.go:21-27.
- **Not established:** Whether `repos/` and `checkouts/` must be on one filesystem. The comment says `clone --local` hard-links objects; no source was read that says what happens across filesystems.

## 3. Evidence, transcripts, diff snapshots

- **Design:** Terminal recordings are asciinema cast files written by `ptyhost` inside the server process: `<data-dir>/transcripts/<run>.cast`, flushed every 2 s, with `.screen` checkpoints and `.retention` files beside; Enhanced and ACP sessions log to `<run>.items.jsonl` in the same directory. internal/ptyhost/ptyhost.go:588, 602, 875; internal/ptyhost/transcript.go:21-22; internal/ptyhost/checkpoint.go:152; internal/ptyhost/retention.go:25; docs/privacy.md:348-358.
- **Design:** They are kept "until you delete the session"; closing the container, reclaiming the checkout and archiving do not remove them. docs/terminal.md:420-424; docs/failure-handling.md:307.
- **Design:** Readers of transcripts: the attach path (replay and history pages), `cloudfield logs`, Export session, and the evidence service, which copies a transcript (cap 16 MiB) into its own directory before writing metadata. docs/terminal.md:420-436; internal/evidence/evidence.go:34-36, 732, 855-860.
- **Design:** Diff snapshots: the git engine's watcher turns file-change quiescence into `run.diff` and `git.branch` events (defaults: quiet 2 s, min interval 10 s, max 60 s) and writes snapshot trees into `<data-dir>/checkouts/<run-id>.diffsnap/`, beside the checkout, so the container never mounts it. Input is bounded at 128 MiB. Readers: the live patch, Changes, and `workspace.timeline`; the events `run.diff` carry the tree ids. internal/gitengine/engine.go:56-64; internal/gitengine/snapshot.go:20-40; docs/local-gateway.md:1620-1670.
- **Design:** Before a checkout is removed, its diff history is moved out of it into `<run-id>.diffsnap/`, reading the session's diff events from the event log. If any step fails the checkout stays and retries back off from 15 minutes to 6 hours. docs/failure-handling.md:1034-1046.
- **Design:** Evidence packets: metadata in the database (`CreateEvidencePacket`), supporting files under `<data-dir>/evidence/`, retained git refs in the workspace repo; 30-day default retention. The server wires the evidence service to the same store, git engine and ptyhost. internal/evidence/evidence.go:34-47, 243-258; internal/server/server.go:513-523; docs/privacy.md:630-635.
- **Design:** Sizes: transcripts, `checkouts/` and `repos/` grow with use, and "`repos/`: Nothing [frees it]. Every push and session branch is kept"; `aether.db` is freed by "Deleting runs or the workspace". Prepared VM checkout disks are sparse 128 GiB filesystems. docs/failure-handling.md:303-310; internal/gitengine/vm.go:31-35.
- **Design:** `docs/install.md` lists `checkouts/`, `transcripts/` and the rest in the data-directory table, but not `evidence/`, `logins/`, `scheduler/`, `assistant/`, `connector/`, `invites/`, `merged/`, `omp-broker/`, `sign/` or `preference-tombstones`, which the server also creates ("The other directories hold internal server state"). docs/install.md:1140-1157; internal/server/server.go:317, 360, 391, 411, 435, 473, 505, 520, 559-560, 740.

## 4. Member homes and agent logins

### Where homes live and how they are mounted

- **Design:** A member's home is `<data-dir>/homes/<member>/`, made on first use with owner-only permissions; package caches are separate under `home-caches/`. internal/server/server.go:406-411; internal/memberhome/memberhome.go:55-80; docs/install.md:1147, 1153.
- **Design:** Into a Docker container it is a Docker `local` volume with `type=none, o=bind, device=<host path>`, named by a hash of the host path, mounted by subpath (the engine "refuses a volume subpath that leaves it"). That needs Docker Engine 26.0 for any mount beneath a member home. internal/runtime/docker.go:395-433; docs/security.md:464-469.
- **Design:** Into a VM it is not mounted: the host's `aether-server vm-monitor`, in the VM's systemd unit, serves a file service on `<vm dir>/home.sock`; the guest mounts it by FUSE, forwarding each operation by path. docs/vm-guest.md:212-232.
- **Design:** In a VM "`flock` and `fcntl` locks hold only within one VM ... A SQLite database or a lock file in the home is not protected against the member's other sessions, as it is under Docker"; "SQLite databases in WAL mode work only among processes of one kernel". docs/vm-guest.md:252-255; docs/harnesses.md:674-677.
- **Design:** The home holds installed agents, agent logins, uploaded configuration and the gh token; "The home survives every stop, save, reset and server restart" and `cloudfield env save` never captures it. docs/environment-home.md:1-5, 17-35; docs/security.md:481.

### Credentials, and where each may and may not be copied

- **Design: default agent login (Claude Code `~/.claude/.credentials.json`, Codex `~/.codex/auth.json`).** Mounted read-write, in place, into every one of the member's containers. Quotes: "Claude Code and Codex replace the refresh token whenever they refresh, so a refresh kept only in the copy would leave your real login revoked." docs/security.md:242-244. "Their own login is mounted in place in all their containers, so a refresh in another of their sessions cannot replace the file yours is mounted over and detach it." docs/security.md:330-332. The server checks the mounted inode before the agent starts. docs/security.md:328-330; docs/teams.md:678-684.
- **Design:** Refresh is the vendor CLI's, in the container. "Cloudfield does not refresh OAuth files." docs/harnesses.md:593-594. The refresh protocol (measured with Claude Code 2.1.317, Codex 0.166.0): Claude Code refreshes about 5 minutes before expiry under the lock `~/.claude/.oauth_refresh.lock`, re-reads the file and skips if it holds a different token; Codex locks `$CODEX_HOME/auth.lock`. docs/plans/2026-11-03-shared-account-credentials.md:42, 55.
- **Design:** The single-copy reason is in the same plan: after a refresh in an old inode, "writing the current login into its old inode forks the refresh-token chain"; and "a blanked shared file breaks new containers too". docs/plans/2026-11-03-shared-account-credentials.md:137-147.
- **Design:** Server-side central refresh of member logins was proposed (pump and central refresh) and then removed: "Phase 1 shipped behind `--session-login-accounts`, failed its live canary, and was removed; shares mount the owner's login as before." docs/plans/2026-11-03-shared-account-credentials.md:7-10.
- **Design:** Exception: the server does refresh the assistant's own sign-in with the vendor and writes the rotated tokens back, to check the account. internal/scheduler/assistant_signin.go:170-182, 312-324; docs/security.md:586-595.
- **Design: shared accounts.** A recipient's session mounts the owner's login file read-write over its own: "Their session uses their own image and home plus your agent login file, mounted read-write because a token refresh rewrites it." The recipient gets a per-session copy of `~/.claude.json` without account keys at `<data-dir>/scheduler/account-config/<session-id>/.claude.json`. docs/security.md:328-333, 367-379.
- **Design:** The sharing risk, quoted: "Root in their session can copy your login file. The refresh token in it outlives a revoke and keeps working until you log out and in again." docs/security.md:408-409. And `/logout` in the recipient's session POSTs the owner's refresh token to the vendor's revoke endpoint "which ends your login everywhere". docs/security.md:410-415.
- **Design:** In session VMs: `copilot` and `antigravity` sessions get a copy of the login made at each cold start of the VM ("a copy of either login is not invalidated when another is used"); `omp` gets no file, it asks a server-run auth broker that holds the one copy in `~/.omp/agent/agent.db` and refreshes it, "so no session's refresh signs another out"; a recipient's omp "receives your access tokens and API keys, never the refresh tokens". docs/security.md:351-365; docs/harnesses.md:742-744.
- **Design: several logins per member (#1142, merged).** The default login stays the files in the home ("never moved, copied or renamed"). An added login lives outside every home at `<data-dir>/logins/<member-id>/<agent>/<login-id>/` (mode 0700, files 0600): `credentials.json`, `anthropic/`, `identity.json` (kind, plan, email, organisation, no secret). One table, `agent_logins(member_id, agent, id, name, position, automatic, shared, created_at)`, migration v115. Only Claude Code; a Console API key is not accepted as an added login. internal/server/server.go:411; internal/store/migrate.go:2675-2687; docs/plans/2026-11-26-multiple-logins.md:121, 155-158; PR #1142.
- **Design:** Signing in an added login runs `claude auth login` in a short-lived container of its own whose mounts put the new login over the default login's three stores; "The server never sees a password, runs no OAuth of its own and never refreshes a token." docs/plans/2026-11-26-multiple-logins.md:213-216; PR #1142.
- **Design:** Single-copy rule for added logins: "Two sessions on one login share its file, as two sessions on the default login do today (pinned mount, rewrite in place). Two logins never share a file, so a refresh of one cannot overwrite another." docs/plans/2026-11-26-multiple-logins.md:203-205. Mounts are volume subpaths so the Docker runtime checks the inode before the agent starts; session VMs refuse an added login because "their mounts are not verified". PR #1142, PR #1148.
- **Design:** Account identity becomes a pair, `domain.Account{Member, Login}`, replacing the bare member id in the quota cache, `fallback.Measured`, `loginKey`, the `account_swap` marker and recovery's comparison; runs and account segments gain `account_login` (migration v116, in #1148, not in the checkout). PR #1142, PR #1148.
- **Design:** The move between logins (#1149, open): the move replaces the session's container, resumes the agent's own conversation and sends one continuation prompt; the target and the `account_swap` marker are written under the launch authorisation lock; the marker records `sending` before the prompt goes out so a restart never resends. Only depletion messages move a session between logins of one account. Not in the checkout. PR #1149; docs/plans/2026-11-26-multiple-logins.md:23-30.
- **Design:** Removing a login is refused while any session is on it, a retained container mounts it, a move marker names it, or a queued sub-session asks for it (#1148). A member merge moves the absorbed member's logins to the survivor with "use for shares" off. PR #1148, PR #1142.
- **Design: gh token.** In `~/.config/gh/hosts.yml`, plain text, in the home; with the public signing key `~/.ssh/aether_signing.pub` and `~/.gitconfig`. "None is in the database". "Root in any of your sessions can read and replace the token". docs/security.md:477-487, 497-499.
- **Design: commit signing key.** "The private key is never in your home." It is `<data-dir>/signing-keys/<member-id>` (0600) and is lent through a read-only SSH agent socket in `<data-dir>/sign/`, mounted at `/run/aether-signing/agent.sock`; in a VM the helper relays the socket. Quotes: "It cannot copy the key or make Cloudfield sign with another one." Cloudfield signs end-of-session commits "with the same key, read from the data directory". docs/security.md:489-499; internal/signing/signing.go:1-6, 37-58; internal/server/server.go:435; docs/vm-guest.md:307-310.
- **Design: workspace secrets.** `<data-dir>/workspace-secrets/<workspace-id>.json`, plain text, 0600, one file per workspace; "The server administrator can read the file, and a backup of it is a credential backup." Injected as environment variables at container creation: "A container keeps the values it was created with". internal/secretstore/secretstore.go:1-2; docs/security.md:552-564.
- **Design: Linear keys.** One file per member, `<data-dir>/linear/<member-id>.key`, 0600, outside the database, never mounted into a container, used only by the server; "The server administrator can read the files." docs/linear.md:104-110; internal/linear/api/keys.go:19.
- **Design: mirror deploy keys** `<data-dir>/mirrors/<workspace>/private_key.<generation>`, and **Slack tokens** in 0600 files under `<data-dir>/slack`; both "readable by the server administrator". docs/security.md:709-718, 1077-1078; internal/slack/tokens.go:22.
- **Design:** Backups hold all of these: "These backups hold every member's agent logins, GitHub tokens, Linear keys and signing keys, the mirror deploy keys and the workspace secrets. Encrypt them, restrict who can read them, and never attach them to an issue." docs/install.md:1168-1172.
- **Design:** Isolated sessions: the login file stays mounted read-write from the home; a whole-directory login such as `~/.omp/agent` stays in the copy so "its refreshes are lost with the session", and on another member's account the launch fails. docs/security.md:240-248.
- **Not established:** Whether a vendor tolerates one login's refresh from two hosts. The docs measure refresh behaviour only inside one host (lock files, inodes); no source read says what the vendor does for two machines.

- **Design:** Cost is per run: `run_costs(run_id, workspace_id, member_id, input_tokens, output_tokens, cost_usd, metered, recorded_at)`, indexed by workspace and by member; a run that moved accounts has a record per segment (`run_account_segments`). Rollups are computed on read. internal/store/migrate.go:480-491, 1620; internal/cost/cost.go:23-48.

- **Design:** Spend is counted "on the account that paid" (segments), per run and per workspace; it is not kept per member as a cap. docs/teams.md:896-898; internal/store/migrate.go:480-491.

## 6. Terminals and live streams

- **Design:** A terminal byte path (Standard session): the agent's PTY runs in the container or the VM; the server's `ptyhost` holds a `runtime.Attachment` to it (Docker attach, or the VM helper's API "in place of `docker exec` and `docker attach`"), keeps a replay ring (`defaultReplayBytes` 1 MiB) and the cast transcript, and fans output to attached clients. internal/ptyhost/session.go:62; internal/ptyhost/ptyhost.go:59-61; docs/vm-guest.md:5-9.
- **Design:** Clients attach two ways. The CLI opens the SSH subsystem `aether-attach` (`SubsystemAttach`). The dashboard's `/ws/attach/<run>` calls `Backend.Attach`: for `cloudfield gui` the SSH backend opens the same subsystem over its one SSH connection; for the server-hosted dashboard `servergw` calls the in-process handler. internal/cli/channel.go:183; internal/webgate/attach.go:61; internal/localgw/backend.go:505; internal/servergw/backend.go:27; docs/local-gateway.md:2653-2700.
- **Design:** Agents' terminals (`cloudfield-internal terminal start`) and session shells survive a server restart through a "keeper" (`aether-internal acp-keeper term`) in the session sandbox that owns the PTY and keeps the newest 1 MiB; the server reattaches by a short-lived exec and "a token only the server holds"; lease holders are recorded in a terminal registry "under the server's state directory". docs/terminal.md:447-477.
- **Design:** What is recorded where: the cast and checkpoints under `transcripts/` (section 3); the terminal registry and sidecars under `scheduler/`; nothing is recorded in the database except through events. docs/terminal.md:411-424; internal/scheduler/state.go:594-596.
- **Design:** The dashboard's event stream is fed only by the in-process `events.InProc` bus (section 1); `/ws/events` takes a `SubscribeRequest` with `after_seq`. docs/local-gateway.md:2576-2606; internal/events/stream.go:20-47.
- **Design:** Gateway-to-server liveness: after 30 s without a byte the gateway sends an SSH keepalive, and after 5 minutes without one drops the connection; a replay-safe call that fails on transport redials once; a call with no answer after 60 s fails with `-32004`. docs/local-gateway.md:202-249.
- **Design:** Through an edge the edge "marks a server offline after 60 seconds without control traffic", and a dead network takes up to six minutes to notice on a link to the edge. docs/local-gateway.md:243-245; internal/edge/proto/limits.go (`ControlIdleTimeout`).
- **Measured** (PR #1175's research README, taken in a 1-CPU sandbox against a real server and gateway, "Nothing here was measured on a live server or on the hosted Edge"):
  - Every request opens a new SSH channel and a `control` subsystem: one call over a 150 ms round-trip link cost 453 ms (3.0 round trips); Lanes' five serial pages 2.33 s. A stream's first byte is 4 round trips "from code". After #1178 (channel reuse) the same measures were 152 ms a call and 0.84 s for five pages. PR #1175 README, cause 2.
  - A 1,000-event page is 356,410 bytes and gzips to 21,634 (16x); `run.list` for 600 sessions is 350,941 bytes, 23,543 gzipped (15x). "Nothing between the gateway and the server is compressed": SSH offers no compression and relay WebSockets have it off. PR #1175 README, cause 4.
  - Cold open: 25 requests, 368 KB, 95% of it `run.list`, 4 to 5 waves; on a 150 ms link the Board shows after 2.9 s on main. A session view issues 10 requests in 30 idle seconds. PR #1175 README, causes 5 and 7.
  - Server time is not the cause: a 1,000-event lane page is under 16 ms median on an idle host; the lane query is index-served. PR #1175 README, "Server time".
  - The relay throttles all splices together to 256 KiB/s once its egress budget is spent, "whether the hosted Edge has a budget is not established". PR #1175 README, cause 4; internal/edge/relay/relay.go:123-127.
  - The edge's per-server connector limit does not apply to the dashboard: its calls "all ride one SSH connection through the relay". PR #1175 README, last paragraph.
- **Not established:** The round-trip time and throughput of a real client through the hosted edge. PR #1175 README, "What I could not establish".

## 7. Client to server

- **Design:** One TCP port, SSH (`:2222` default). "Git, the control channel, terminals and `ssh` into a session all travel over that one connection." The server opens no HTTP port unless `web-port` is set (tailnet-only HTTPS). docs/networking.md:3-6, 244-247.
- **Design:** Channel types: `session` and `direct-tcpip`; every other type is rejected, and every global request (including `tcpip-forward`) is denied. internal/sshd/server.go:679-704.
- **Design:** On a `session` channel: `pty-req`, `window-change`, one `exec` (only `git-upload-pack`/`git-receive-pack <workspace>`), or one `subsystem`. Subsystems: `aether-control` (JSON-RPC), `aether-events`, `aether-attach`, `aether-acp`, `aether-assistant`, `aether-terminal`, `aether-dev-browser`, `aether-dev-artifact`, `aether-sync`, `aether-run-ssh`. A gated client is refused every subsystem but control. internal/sshd/session.go:56-135; internal/protocol/protocol.go:18-28; internal/protocol/acp.go:7; internal/protocol/assistant.go:447; internal/protocol/development_stream.go:12-13; internal/protocol/run_ssh.go:9.
- **Design:** `direct-tcpip` targets: `terminal` (the member's environment terminal container), `run:<run-id>` (a port in a session, needs Steer); forwards "reach only the session's own loopback". internal/sshd/forward.go:27-67; docs/security.md:875-882.
- **Design:** Identity, direct path: a registered SSH public key (stored canonicalised, unique), a tailnet login by local `tailscaled` WhoIs (tagged nodes refused; `--tailnet-require-key` demands both), invite codes carried in the SSH user name, and a first-key bootstrap that is accepted only over the tailnet or from the host. internal/store/store.go:31-43; docs/networking.md:72-111; internal/sshd/server.go:34-48, 710-740.
- **Design:** Identity, relayed path: a separate SSH config offering public-key auth only, where the key must be the grant's device key; no tailnet WhoIs, no bootstrap, no invite or claim names. The grant is the edge's signed statement (60 s lifetime, 30 s skew, 8 KiB) naming account, device id, device key, server id, connection id, kind and issuer. The server maps the account to a member through `member_identities(provider, subject) -> member_id` and approves the device in `member_devices`. internal/sshd/edge.go:62-120; internal/edge/proto/grant.go:15-45; internal/store/migrate.go:1317-1356.
- **Design:** Server id: `lower(base32-nopad(sha256(host public key wire bytes)))[:26]` (130 bits), from `<data-dir>/ssh/host_ed25519_key`, generated on first use. "Clients check the host key against it on every connection." internal/edge/proto/id.go:15-25, 40-47; internal/sshd/hostkey.go:13-47; docs/edge.md:37, 214-215.
- **Design:** Client banner `SSH-2.0-Aether <version>+b.<build>` lets the server gate old clients, section 9. internal/sshd/clientgate.go:18-30; docs/install.md:1105-1109.
- **Design:** Several server links on one client. `config.json` holds a default link in its top-level fields plus `links`, named profiles (`cloudfield link --name`), and `gui_server`; each profile has its own `addr`, `user`, `key`, `known_hosts`, `edge_url`, `server_id` ("EdgeURL and ServerID are this profile's own and never inherited: a server id pins one server"). The linked clones (`repos`) are one list "across every server this computer links: workspace ids are unique, so no link owns them". internal/cli/config.go:19-100; docs/install.md:721-731.
- **Design:** Device keys and tokens are per edge: `<config dir>/edge-device-key` (one key per machine) and `edge-tokens.json` (a device token for each edge). docs/install.md:730-731.
- **Design:** `cloudfield gui` and the local gateway hold, per process: one `sshBackend` (one lazy shared control connection to the linked server), one `localState` (the config, a `SyncManager`, a `ForwardManager`, the in-progress edge sign-in) and one bearer token. `--server <name>` serves one named profile; `link.switch` swaps the connection in place, stops the forwards and syncs first and saves `gui_server`. "The gateway keeps one current repository per server profile." The workspace selection is stored per `sha256(addr + member id)`. internal/localgw/backend.go:25-40; internal/localgw/local.go:86-100; internal/localgw/localgw.go:66-92; internal/localgw/workspace_selection.go:30-37; docs/local-gateway.md:37-52, 1959, 2148-2152.
- **Design:** The edge path also reports `edge_path.online`, the account's other servers the edge sees online, so a client can name a server reinstalled under a new id. docs/local-gateway.md:284-309.
- **Design:** The server-hosted dashboard identifies each request by tailnet WhoIs and dispatches in-process; it is never refused as an old client. docs/local-gateway.md:13-16, 273-282.

## 8. Edge

- **Design:** What the edge is: a relay both sides dial out to. "The edge splices the two outbound connections. SSH runs end to end between client and server, so the edge cannot read it. The edge says who signed in; the server alone decides what that person may do." docs/edge.md:3-4, 28-31.
- **Design:** Enrolment. The server (agent) opens a WebSocket control channel to the relay; the edge sends a `Challenge` (nonce, origin); the server answers `Hello` (host key, `SignEnrollment` signature over origin, server id and nonce with the host key, agent version, name, access policy); the edge returns `Ready` (server id, state `unclaimed`/`claimed`, the edge's signing key, relay origins). The server pins the edge key on first connection. internal/edge/proto/control.go:43-95; internal/edge/proto/enroll.go:104-126; docs/edge.md:67-69.
- **Design:** Files under `<data-dir>/edge/` (dirs 0700, files 0600): `edge_key.json` (pinned edge key), `owner.json`, `claim.json` (claim code hash, expiry, attempts, optional admin), `status.json`, `lock`, `keys/` (one directory per pinned edge key, with the owner held under that key), `edge_state.json`. The state is "shared" by the serve process and the `aether-server edge` commands, so "every method reads the files afresh". internal/edge/agent/state.go:19-49.
- **Design:** Who dials whom: the server dials the edge's control channel and keeps it (ping 20 s, idle timeout 60 s, reconnect backoff 1 s to 60 s). The edge sends `Open{conn_id, ticket, kind, grant}`; the server dials a data socket back to the edge with the ticket within 10 s; the client dials the edge with its device token and the edge issues the grant. internal/edge/proto/control.go:96-110; internal/edge/proto/limits.go:42-61; docs/edge.md:18-31.
- **Design:** What the edge stores per server (`edge.db`): `servers(id, name, kind self-hosted|hosted, access_policy, owner_type, owner_account_id, claimed_at, relay_origin, enrolled_at, agent_version)`; `directory_entries(server_id, kind, provider, subject, login, email, role, expires_at)` replaced each time the server pushes its directory (limit 1000 entries per message); `account_reach(provider, subject, server_id)`; `blocked_servers`; `pending_account_deletions(server_id, ...)`; `connector_use(server_id, relay_origin, last_used_at)`. internal/edge/store/edgestore.go:204-261, 263-277; internal/edge/proto/control.go:17-18, 144, 317-318; docs/privacy.md:306-324.
- **Design:** Relay limits: 48 concurrent SSH connections per server, 16 per device, 8 HTTP (connector) connections per server with at most 16 waiters, 4 long connector calls per server (enforced by the server), 3 unclaimed servers per client address, 10 s attach deadline, 15 s HTTP connection wait, 30 s hold for a returning server. After the monthly egress budget is spent, all splices share 256 KiB/s. "No idle timeout applies to a spliced stream". internal/edge/proto/limits.go:9-61; docs/edge.md:714-741; docs/edge.md:1247-1255.
- **Design:** Connector addresses: the universal `https://<edge>/mcp` ("one URL for every Cloudfield server"), whose sign-in page lists the account's servers with name, id, role and whether each asks for a code, "even when you have only one server"; and the per-server `<edge>/mcp/<server id>`. A server's connector base URL embeds its server id; tokens are bound to the URL they were issued for. docs/connectors.md:22-23, 164-177; internal/server/server.go:736-745; docs/edge.md:1043-1050.
- **Design:** Does the model have a group of servers or one account owning several? An account can already own several servers: `servers.owner_account_id` is a foreign key with an index (`servers_owner`) and no uniqueness, and `account_reach` records every server an account may reach; `cloudfield servers` lists "servers your account reaches". There is no table, column, message or limit that names a group, fleet or cluster of servers; the relay keeps each server as an independent registration keyed by server id (`servers map[string]*registration`). internal/edge/store/edgestore.go:204-214, 256-261; docs/edge.md:305; internal/edge/relay/relay.go:178-180. (Absence of any group concept is from reading edgestore.go, control.go and relay.go; the other edge packages were not read line by line.)
- **Design:** Can two machines share one server id? The id is a function of the host key, and the enrolment proof is a signature by that key, so any host holding `host_ed25519_key` passes enrolment as that server. The relay then keeps exactly one registration per id: a new enrolment replaces the old (`r.servers[id] = reg`, then `old.cancel(errReplaced)`). A client that connects through the edge is spliced to whichever machine enrolled last. Directory, owner and claim are keyed by id, so they would be shared. Direct and tailnet connections are by address and unaffected. internal/edge/proto/id.go:21-25; internal/edge/proto/enroll.go:104-110; internal/edge/relay/control.go:218-226; internal/edge/store/edgestore.go:204-226. (From code; never run with two hosts.)
- **Design:** The docs treat the host key as the identity: "Back that file up: a new host key is a new server that must be claimed and linked again." docs/edge.md:214-215.
- **Design:** The edge is a single process: its registrations, rate-limit counters and egress counter are in memory, with the monthly egress counter persisted. internal/edge/relay/relay.go:50-70, 178-230.
- **Not established:** How the edge behaves when two live hosts enrol the same server id repeatedly (flapping rate, grant handling); only the replace rule was read.
- **Not established:** Whether any client or server code assumes one edge account maps to one server; `cloudfield link` takes one server id per link, which is the only single-server assumption read.

## 9. Updates and release channels

- **Design:** Server self-update: a super admin (or root on the host) runs `cloudfield server update` or `sudo cloudfield-server update`. It checks the signature, replaces `aether-server` and the `aether` beside it, keeps `aether-server.prev` and `aether.prev`, takes the database copy if the schema changes, restarts the service, and rolls back both if the new server does not finish starting. docs/install.md:768-783.
- **Design:** The server can update itself: every 6 hours it checks its channel's signed pointer and schedules the update for the next idle moment (no session working, no terminal attached, no SSH connection into a session). `AETHER_NO_UPDATE_CHECK=1` turns it off. Pending, declined and last-attempt records are in the database; marks in `server-update/check.json`. docs/install.md:938-961, 973-976, 914-915; internal/store/serverupdate.go:96-243.
- **Design:** An update lock is a `flock` on `<data-dir>/server-update/update.lock`, so only one update runs on a host. internal/serverupdate/stage.go:12-29.
- **Design:** Channels: `stable`, `beta`, `nightly`; the server follows one, `release_channel`, a database setting a super admin changes; releases are ordered by the signed manifest's `(build, hotfix)`, not by tag. docs/install.md:839-867, 1094-1103; internal/store/serverupdate.go:269-300.
- **Design:** Signed manifest: `aether-release.json` plus an ed25519 `.sig`, verified against a key built into the running binary; it lists each asset's SHA-256 and size, `channel`, `build`, `hotfix`, `store_schema` and image digests. docs/install.md:1085-1113; internal/selfupdate/manifest.go:60-72.
- **Design:** Version rule between client and server: "A server refuses any client older than itself." The client announces `v<version>+b.<build>` in its SSH banner; a client with a lower build (or, when either has none, a lower version) gets `rpc error -32005: this aether is ... update this client first`. `server.info` and `server.update_status` stay callable; `direct-tcpip` is refused too. "Development builds ... are never refused." The in-process client is never gated. The gate "is not access control". docs/install.md:765-766, 1072-1083, 1105-1112; internal/sshd/clientgate.go:21-33, 49-70; internal/sshd/server.go:696-698.
- **Design:** `server.info` reports `build` and `min_client_build`; the client matches its server by build. docs/install.md:1105-1109; internal/sshd/clientgate.go:52-59.
- **Design:** The edge has its own compat floors: the manifest's edge block carries `store_schema`, `store_compat_floor` ("the oldest schema a binary must support to open a database this release has migrated"), the protocol `version` and `min_version`, `min_upgrade_from` and blocking manual steps. The edge protocol is at version 6 with `MinVersion` 1, and "A newer peer is accepted". There is no compat-floor field for the server's own store; the server refuses a downgrade by schema. internal/selfupdate/manifest.go:76-100; internal/edge/proto/edgeproto.go:13-45; docs/edge.md:1043-1059 (the version table); internal/serverupdate/preflight.go:110-116.
- **Design:** Saved VMs across versions: "Running VMs keep [their Cloud Hypervisor and guest kernel], and their helper disk, until they stop"; "a running or saved VM boots [the release kernel] on its next cold start"; a VM saved before an upgrade "keeps its old settings on wake until its next cold start". The helper is the `aether-server` binary on a read-only helper disk (`/init`). A helper restored from a save "can be older than the server"; when its protocol differs from `guest.Protocol` (now 2), `Ping` fails with `guest.ErrIncompatible` "and the session needs a cold start". Fields added to the API do not change the number. docs/install.md:802-806; docs/vm-guest.md:7-13, 76-82, 207-210, 730-737; internal/guest/client.go:26.
- **Design:** What the update ships for VMs: `cloudfield-server vm install` places Cloud Hypervisor v54.1 (pinned, SHA-256 checked), the release's guest kernel `aether-vmlinux-x86_64` at `/usr/local/lib/aether/vmlinux` (checked against the signed manifest; `vmlinux.release` notes the release) and the pinned oh-my-pi at `/usr/local/libexec/aether/omp`; "the update replaced the binary each VM's monitor runs", so a package upgrade that restarts `aether-vm-*` units "loses its session". docs/install.md:100-121, 802-811.
- **Design:** Rollback restore: a server started by its unit puts its release's Cloud Hypervisor and kernel in place before starting any VM, "That covers an update from a client or the dashboard, and a rollback." docs/install.md:806-811.
- **Not established:** Whether a saved VM memory image survives a Cloud Hypervisor version change or a different host CPU. Only the helper protocol check and "boots ... on its next cold start" were found.

## 10. Members, roles and workspace access

- **Design:** The role policy is a pure package with no I/O: `internal/permissions` maps (actor role, workspace reach, run owner, protected flag, steer-others setting) to the capabilities View, Steer, Kill, Message, Launch, Push, admin. "A super admin is admin everywhere, an admin is admin in the workspaces they own and a collaborator in those they were granted, and a collaborator or viewer keeps their role in the workspaces they were granted. A workspace has one owner and per-member grants; the same handlers serve the SSH control channel, `cloudfield gui` and the server-hosted dashboard. docs/teams.md:203-216, 388-420; docs/local-gateway.md:5-8.
- **Design:** What a super admin can do to the host: replace the server's binaries without a shell on the host ("a super admin can already run any code on the server's Docker daemon"), change the release channel, run the Sysbox installer as root from the dashboard, and run sessions at the Root tier. An admin gets no implicit access to anyone's account ("Sharing is one-way. "what a server holds is its administrator's." docs/install.md:1168-1172; docs/linear.md:110; docs/security.md:552-554, 560-561, 717-718, 1077-1078; docs/privacy.md:344, 553-555, 621-629.
- **Design:** Members are in the database (`members`, `member_identities`, `member_devices`, workspace owner and grant tables); member homes and logins are on disk; `member remove` deletes the home, the logins directory and the key files and refuses while anything points at the member. docs/privacy.md:621-629; PR #1142.
- **Design:** Approval is a state: tailnet and edge joiners start pending unless auto-join is set; `edge-access` (`account` or `approved-devices`) decides whether a new device waits for a person. docs/networking.md:76-89; docs/edge.md:50-56.

## 11. Remote development and syncd

- **Design:** The client-side sync daemon is "a pure SSH client": it follows the server's event stream, mirrors server-owned run branches (`aether/run-*`, `cloudfield/run-*`) into the local clone's remote-tracking refs, pushes the local base branch up on a poll (15 s) and reconnects with backoff; "It only ever moves refs - the working tree is never touched." internal/syncd/syncd.go:1-6, 36-48.
- **Design:** One daemon links one server: its config takes `Server` or `ServerID` (+ `EdgeURL`), pinned to that server's host key, and one `RepoPath`. internal/syncd/syncd.go:50-58, 127-135, 350-352; docs/install.md:739-762.
- **Design:** The remote-development plan (implemented in PR #247 of the former repository name) runs every agent, terminal and browser on the server; the client's role is forwarding and rendering. The plan reuses "the session checkout, shell PTYs, terminal emulator, gateway, controller fencing, evidence storage" and says "Add no separate development workspace, jobs platform ..."; hosted browser traffic travels "through your Cloudfield server". docs/plans/2026-09-25-remote-development.md:1-8, 18-40; docs/privacy.md:372-375.
- **Design:** Cloudfield work on a machine other than the server: the only client-side machinery found is the local gateway's `/local/v1` verbs (port forwards, a sync manager for `cloudfield sync --live`, repo push/pull and fast-forward, git identity), which run on the caller's machine and move files and refs, not agent work. The VM-side endpoint of `sync --live` runs in the session on the server. docs/local-gateway.md:28-35, 1939-1960; internal/localgw/local.go:62-100; docs/vm-guest.md:658.
- **Design:** The runtime seam names a future: "future backends (Podman, firecracker, remote runner nodes) implement the same interface". No remote runner exists; the runtime is built once at startup (`s.rt = cfg.Runtime`). internal/runtime/runtime.go:1-5; internal/server/server.go:328-369.
- **Design:** "Handoff" in the code is a transfer of a session between members on the same server (`store/handoff.go`, `aether handoff`), not between machines; a handed-off session "stays on the launcher's account". docs/security.md:437-438; internal/store/handoff.go (file name only).
- **Design:** The execution-separation decision: "Cloudfield does not currently split a native agent from its tools". docs/agent-execution-separation.md:1-9.
- **Not established:** Any code path that starts a Cloudfield session, agent or container on a host other than the one running `aether-server`. Searched `docs/*.md` and `internal/` for "remote runner", "other machine", "multi-host" and found only the runtime interface comment and an edge canary note (docs/edge.md:1162).

## 12. Push, Slack, Linear, assistant, watches: per-server singletons?

For each, what the code says about its process state; whether sharing one database between two servers would break it is stated only where the code settles it.

- **Push:** A bus consumer in the server process ("The service is a bus consumer"); subscriptions are database rows (`PushStore`), the VAPID key is a file, `<data-dir>/push/vapid_key.pem`, created on first use; it waits a quiet period of 1 minute per member and keeps an in-process digest ticker. It listens to the local bus only, so a second server on the same database would not hear the first's events (section 1). internal/push/service.go:1-14, 36-40, 73; internal/server/svc_push.go:16-29; internal/push/digest.go:151; docs/security.md:763-775.
- **Slack:** One outbound Socket Mode websocket per server process, with the two Slack tokens in `<data-dir>/slack`; started only when tokens exist; it hears needs from the push service and acts through the in-process connector path. Per-server singleton by construction: one set of tokens, one connection. What Slack does with two connections on one app is **Not established**. internal/slack/slack.go:1-5; internal/slack/socket.go:1-40; internal/server/svc_slack.go:16-39; docs/security.md:1056-1079.
- **Linear:** No poller found: a key per member in `linear/<member-id>.key`, read on demand by the server for that member's own calls; it "only reads". Per-server only through the key files. internal/linear/api/keys.go:19; docs/linear.md:1-10, 104-110. (`time.NewTicker` grep over internal/linear returned nothing.)
- **Assistant:** A per-member sandbox container on the server's runtime, home `<data-dir>/assistant/<member>/home`, with the sign-in kept in that home and refreshed by the server; cards and queue are in the database. Per-server by its home and container. docs/security.md:571-604; docs/assistant.md:16-27; internal/store/assistant.go (file name only).
- **Watches:** A `time.NewTicker` poller in the server process evaluates watch rows (a member's own gh token) and, for pull requests, polls GitHub ("GitHub sends Cloudfield no webhooks, so the server polls"); state is in the database. Two servers over one database would each poll and each notify: that follows from the poll loop being unconditional in the service, read at internal/watch/service.go:441 but not traced further. docs/watches.md:109-126; internal/watch/service.go:441.
- **Design:** The connector HMAC key is `<data-dir>/connector/hmac.key`, and the connector's base URL embeds the server id, so connector tokens are per server. internal/server/server.go:736-745.
